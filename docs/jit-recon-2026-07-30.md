## Orientation — what this recon was for

Tony's plan (written down 2026-07-29, `docs/jit.md` §0) is that **the JIT becomes the interpreter** —
one execution path, and in the end it is the compiled one. Not an accelerator running beside an
interpreter that stays. Under that plan the expensive part of the work is *not* LLVM IR generation
(mem2reg is landed, so an emitter never constructs SSA — naive alloca/load/store per local, let the
pass build the phis). The expensive part is **how much of the interpreter has semantics that were
never written down.** This recon went looking for that.

It answers five named questions: **J0** the triage of the `incant/jitscratch` SIGSEGV; **J1** the
`jitEmit*` inventory and the coverage boundary it defines; **J2** the cold-reader gap between what
`jit.md` §0 says and what the source alone implies; **J3** where the interpreter is reachable from a
jitted path; **J4** the upload bundle for a design reasoner.

### THE HEADLINE

The `jitscratch` crash is a **one-condition bug and an afternoon's fix** — `runOP`'s JIT
operand-seeding gate is written `if jitting && op.isOperator`, but every unary operator in incant
(`++`, `--`, prefix `-`, `!`, `@`, `**`, `=*`) is registered `ruleMethod=`, i.e. **isMethod, not
isOperator**, so no unary operand is ever seeded and `jitEmitUnary` dereferences a null `jitData`.
**But fixing it buys almost nothing, because the crash is not the problem.** The problem found
behind it is that **there is no crossover boundary at all**: `jitExecBlock` runs the action's `BlocK`
through the ordinary interpret walk, so under `jitting=1` every construct *without* a gate simply
**executes for real, silently, at emit time** — proven by a jitted `print` that printed `hello world`
during compilation. Exactly **18 of 42 operators and 1 of 30 statement handlers** carry a gate; the
other 53 sites are silent interpreter fallbacks that nobody declared. The sharpest demonstration is
not the crash: `jitEmitGIF` **has no else arm**, so a jitted `if/else` whose condition is false
**exits 0, leaves the variable wrong, and returns garbage** (`maximus` stayed 11 where 7 was correct;
return value `83623936`). A wrong answer with a clean exit status is worse than a segfault, and it is
the concrete instance of `jit.md` §0's open ruling arriving as a schedule artifact rather than a
decision. **The JIT does not need an emitter census so much as it needs a refusal mechanism and an
IR verifier — neither of which exists today.**

## J0 — the 139, and what it gates

**Verdict: the crash is an AFTERNOON. Declaring the JIT exercised again is an ARC.**
**Confidence: high on both halves** — the crash cause has three independent confirmations, and the
"more behind it" half rests on four independently-failing probe runs, not on reasoning.

### The crash, exactly

```
0  jitEmitUnary  GroupRules.mm:3227:36   llvm::Value *v = target->jitData->jitValue;
1  opPlusPlus    GroupRules.mm:4957:11   return jitEmitUnary(result, jitInc);
2  runOP         GroupRules.mm:6290:12   result = op->groupBody->gMethod(target);
3  aCTionBlocK   GroupRules.mm:54:13
4  jitExecBlock  GroupRules.mm:3274:3
5  jitRunAction  GroupRules.mm:3397:2
6  testing       GroupRules.mm:6690:10
```
"Bad pointer dereference at `0x0000000000000008`" — `jitData` is **null**, and `jitValue` sits at
offset 8. `target` was never seeded.

### Why it was never seeded — one condition, and three confirmations

`runOP`'s JIT operand-seeding gate (`GroupActions.rtn:642`, generated to `GroupRules.mm:6273`) reads:

```
if jitting && op.isOperator {
    -%  if (target && !target->jitData) { … jitSeedLiteral / jitSeedField … }
        if (arg    && !arg->jitData)    { … } %-
}
```

Immediately below it, `runOP` dispatches on two mutually exclusive branches
(`GroupActions.rtn:654-655`):

```
if op.isOperator    result = op.operat(arg,target);     <- seeded
or op.isMethod      result = op.method(target);          <- NOT seeded
```

1. **The crash frame** lands on `GroupRules.mm:6290`, which is the `op.isMethod` branch — not 6287,
   the `isOperator` one. So the operand went down the arm the seed gate does not cover.
2. **The registration** (`incant/setup`) makes every unary operator an `isMethod`, because they are
   declared with `ruleMethod=`, not `operateMethod=`:
   `:89 negate unary ruleMethod=opUnaryMinus` · `:99 '=*'` · `:120 '--'` · `:122 '**'` ·
   `:125 '++' unary ruleMethod=opPlusPlus` · `:131 '@'` · `:135 '!'`.
3. **All three unary POPs die identically.** `jitInc` → 139, `jitDec` → 139, `jitNeg` → 139, each in
   its own process, each on the same frame. One cause, three symptoms — not three bugs.

The gap is also **already documented in the source, at the crash site**. `jitEmitters.rtn:227-229`
carries: *"NOTE: not wired yet — the unary expression flows through aCTionTokenXP -> a uxp node ->
runOP, bypassing aCTionExpressioN's binary-shaped jitting gate, so no gate currently reaches
opPlusPlus/opMinusMinus under jitting."* That comment is **true today and contradicts `jit.md`'s
Phase-1 table**, which records `jitInc`/`jitDec`/`jitNeg` as DONE with results 14/12/-13.

### Why it used to work and stopped — a regression, dated

`jit.md:291` describes the *old* route: *"Unary dispatches via `aCTionExpressioN`'s jitting branch
detecting the `uxp` node … seeding the operand, and firing `arg.method(arg)`."* That branch lived in
`jitXP`, and `jitXP` **was folded out on 2026-06-30** in the unified-emit-on-walk pivot
(`ruleActions.rtn:286`, `:300-302`). Its seeding responsibility moved to `runOP`'s new gate — but the
new gate was written for the binary/`isOperator` shape and the unary/`isMethod` shape was left
behind. Nobody noticed because `Commands.rtn`'s `testing()` had been hijacked to call the
now-retired `runScaf`, so `jitscratch` did not reach `jitRunAction` at all between the pivot and
2026-07-29. **This is a scope note, not a reproach:** `jitscratch` was never a passing baseline in
that window, exactly as `docs/wakeup.md:773-782` already says. *(Regression attribution: inferred —
the fold-out comment and the date ordering support it, but no bisect was run.)*

### The scope answer, honestly

The **fix** is local and small: seed for the `isMethod` operator branch too (or move the seed above
the dispatch). That is an afternoon, and its correctness is testable by the three unary POPs.

**What it does not buy is a working JIT**, and this is the load-bearing half of J0. Behind `jitInc`
sit at least three further failures with *different* causes, each found in one run:

- **Loops abort, on a different bug.** `testWhilE` and `testDo` both die at **134 (SIGABRT)** on
  `Assertion failed: getOperand(0)->getType() == getOperand(1)->getType() && "Both operands to ICmp
  instruction are not of the same type!"`. The likely mechanism — *inferred, not verified* — is that
  `jitEmitCompare` and `jitEmitBinary` both end with `target->jitData->setJitter(res)`, i.e. they
  **overwrite the target operand's stored SSA value with the result**. On the loop's second pass the
  same field node is compared again, but its `jitValue` is now the **i1** the first compare left
  there, so LLVM is handed `icmp i1, i32`. Harmless in one-shot straight-line expressions, fatal the
  moment a node is used twice. This is structural: `jitData` hangs off the GroupItem, so a node can
  hold exactly one SSA value at a time.
- **Multi-statement actions segfault.** `testGXLeaf` (two `if`s in one body) → 139.
- **`if/else` silently returns a wrong answer** — see J1 and the headline.

So: **one afternoon to stop the crash; an arc to make the JIT trustworthy.** The honest framing for
Tony is that the `++` fix is worth doing *because it is cheap and unblocks fixture capture*, not
because it moves the frontier.

**Confidence: high on the inventory (source-enumerated and cross-checked against a prior recon);

`jit.md` §0's OPEN ruling — *what happens to a construct the JIT cannot emit yet?* — cannot be

### 1c. What is genuinely UNKNOWN (not "covered", not "uncovered")

Per the brief: anything unsure goes here, not in "covered".

- **Whether a gated op is *correct*, as opposed to present.** 18 gates exist; 24 POPs pass. The
  `testIfElse` result below shows a gate can be present, fire, and still be wrong.
- **`opAssign` with a byRef (`:=`) argument.** The gate returns before opAssign's own byRef branch.
  Never exercised; unknown whether `jitEmitAssign` mis-stores or happens to work.

  coverage gap.
- **Everything downstream of the first failure in a given body.** Because failures are crashes and
  aborts, a body's later constructs are never reached, so absence of a report is not evidence of
  health.

## J2 — the cold-reader gap

**Confidence: high.** This is a documentation-state question and the state is checkable.

### What §0 says

> **Tony's plan is that the JIT BECOMES the interpreter.** It is not an accelerator running beside
> an interpreter that stays. There is one execution path, and in the end it is the compiled one.
> …
> ### Consequence 1 — locals-as-frames lands ONCE, in the JIT
> `saveLocalFields` gets **DELETED, not repaired.** … Do not spend effort making the interpreter's
> activation record correct; it is a component with a scheduled death.
> ### Consequence 2 — the OPEN RULING …
> **During the crossover, what happens to a construct the JIT cannot emit yet?**
> Falling back to the interpreter *is* the divergence — reappearing as a **schedule** artifact
> rather than a design one, which is worse because nobody wrote it down as a decision. … **it is
> Tony's to rule on.**
> — `docs/jit.md:9-49`

### What the source alone implies

**An accelerator, unambiguously, and at every altitude.** A reader who has not read §0 encounters, in
roughly this order:

- **`GroupRules.twk:77`** — `jitting` is a *one-bit mode flag* in `GroupRules`, sitting in the same
  bool block as `generating`, `defining`, `debugGuards`. A mode you can be in reads as a mode you
  can be out of. Modes are optional; replacements are not.
- **`Instruct.rtn`, 18 sites** — every gated op has the identical shape:
  ```
  if jitting {
      -% return jitEmitBinary(argument, target, jitAdd); %-
  }
  <the entire interpreted body, still here, still compiled, still the else-case>
  ```
  The interpreted body is **immediately below the gate in the same function**. The plain reading is
  "fast path above, real path below." The design intent — `jit.md:229-235`, that at endgame the
  interpret body and the gate strip out mechanically and *the opMethod IS the emitter* — is stated
  only in `jit.md`, never at any of the 18 sites.
- **`GroupActions.rtn:642` and `ruleActions.rtn:538`** — same shape, same reading.
- **`jitEmitters.rtn:431-440`** — `ruler->jitting = 1; … jitExecBlock(action); ruler->jitting = 0;`
  A gate raised and lowered around a region is the canonical accelerator idiom.
- **`Commands.rtn:623` (`testing`)** — the JIT's only entry point is a *"scratch verification
  harness"* reached through a command literally named `testing`. Nothing in the tree invokes the JIT
  on a production path.
- **`docs/jit-coverage-recon.md`** — an otherwise excellent document that recommends `jitBail`
  whole-action fallback (§ finding 1) as the *design answer* for `aCTionFOR`. Under "accelerator"
  that is obviously right. Under §0 it is precisely the divergence-as-schedule-artifact §0 warns
  about. This is the misreading having already been committed to a doc.

**That gap is what bit on 2026-07-29** (`docs/wakeup.md:44-50`): a reasoner derived "accelerator"
from the `jitting` gate and argued for **repairing the interpreter's frame handling** — work §0
says explicitly not to do, because `saveLocalFields` is scheduled for deletion, not repair.

**Current mitigation is two doc lines and nothing in the code.** `jit.md` §0 itself, and
`jit-design.md:18-22` which points at it. **Zero of the 20 gate sites carry a pointer**, and the
gate sites are what a cold reader reaches first. The cheap, in-character fix — *not applied, this is
a read-only recon* — is one comment line at `GroupRules.twk:77` where `jitting` is declared, since
that is the definition every gate resolves against.

## J3 — interpreter reachability from a jitted path

**Verdict: the question understates it. The interpreter is not *reachable from* the jitted path —
today the jitted path IS the interpreter, running for real, with emit as a side effect.**
**Confidence: high — this is a run result, not a reading.**

### The bones

Probe: `testing(testPrint)`, where `testPrint code={ print "hello" name:; }` and `name = "world"`.

```
PROBE: about to jit testPrint (a non-gated print inside a jitted body)
=== jitRunAction: entering on testPrint ===
hello world                                          <-- PRINTED AT COMPILE TIME
=== jitRunAction: no result emitted (gate did not fire?) ===
PROBE: done
```
Exit 0.

`aCTionPrinT` has no `jitting` gate, so it did what it always does: it printed. Nothing was emitted;
the driver returned -2. The interpreter did not "fall back" — it never stopped running.

### The mechanism

`jitRunAction` (`jitEmitters.rtn:431-439`) raises `jitting=1`, then calls `jitExecBlock`, whose
entire body is:
```
extern GroupItem jitExecBlock(GroupItem input)
{
GroupItem   BlocK:;
    if BlocK    BlocK.gMethod(BlocK);
    return input;
}
```
That is the *interpreter's own* `aCTionBlocK` walk. Every statement is executed. A gated op returns
early after emitting IR (so its interpret work is skipped, and the runtime value never updates); an
ungated op or statement handler **does its real work, with real side effects, at emit time.**

### The seam inventory — every site where interpretation happens inside a jitted body

1. **All 24 ungated operators** (§J1b). Under `jitting=1` they execute interpretively and emit
   nothing. `opPrint`, `opString`, `opSetGroup` (`:=`), `opSetTag`, `opAddAttribute`,
   `opReplaceMember` etc. all *mutate the live GroupItem tree* while "compiling."
2. **All 29 ungated statement handlers** (§J1b) — including `aCTionWhilE`, `aCTionDO`, `aCTionFOR`,
   `aCTionPrinT`, `aCTionIterate`, `aCTionSearch`, `aCTionDefinE`.
3. **Loops execute rather than emit.** `aCTionWhilE` really loops at emit time — but its condition's
   ops are gated, so the condition value never updates in the interpreter and the loop cannot
   terminate normally. Observed outcome is the LLVM ICmp abort (134) before that matters.
4. **`runOP`'s three non-operator arms** (`GroupActions.rtn:656-660`): `or isRule → runRule`,
   `or actionType → runAction`, `or isMethod → method(arg)`. **A call from inside a jitted body runs
   the callee interpreted, entirely.** This is also where `jitEmitCall` would attach.
5. **`opPlusEQ`'s fall-through** (`Instruct.rtn:706`): its gate type-checks the target and, for
   `isLIST`/buffer/`isSTAK`, **falls through to the interpreted body silently** while `jitting=1`.
   `jit-coverage-recon.md` correctly flags this as the one op that type-checks *and* the one that
   silently degrades.
6. **`jitEmitGIF`'s missing else arm** — the else statement is simply never visited by anything, so
   it is neither emitted nor interpreted. It vanishes.

### The one LOUD refusal that already exists — and it is the precedent for the open ruling

`Instruct.rtn:722` (`opPlusPlus`) and `:566` (`opMinusMinus`):
```
if result.isIterator {
    if jitting  cerr "ERROR ++ on an iterator is not JIT-supported yet:",result.tag:;
    return iterAdvance(result,1); }
```
**This is exactly `jit.md` §0's candidate answer — "degrade to the oracle LOUDLY" — already
implemented, once, in the whole codebase.** Whoever wrote it (2026-07-29, the iterator work) reached
the same conclusion §0 leaves open. It is worth putting in front of Tony as evidence the candidate
answer is the natural one, and as the shape to generalise: *say so, then degrade.* The other 52
degradation sites say nothing.

### The worst case, and it is not a crash

Probe: `testIfElse code={ if righty > 0; maximus = righty * 2; else maximus = 7; }`.

| setup | correct | JIT produced | exit |
|---|---|---|---|
| `righty = 13`, `maximus = 11` | `maximus = 26` | `maximus = 26`, ret 26 | 0 |
| `righty = -7`, `maximus = 11` | **`maximus = 7`** | **`maximus = 11`**, ret **83623936** | **0** |

The taken case is **correct by luck** — it exercises only the arm `jitEmitGIF` emits. The not-taken
case leaves the variable untouched and returns a garbage integer, **with a clean exit status and no

- `jitRunAction` caps with `CreateRet(gJitResult)`, and `gJitResult` at that point is an SSA value

  compiled and ran anyway because —
- **`llvm::verifyFunction` is never called.** Grepped the whole tree: the only occurrences are in

- **There is no IR dump facility either.** No `mod->print`, no `llvm::errs()` in `jitEmitters.rtn`.
  The 2026-06-27 IR dump that refuted the `jit-gif-branches` claim must have been a hand-added,

  a `.ll` file gives the JIT "a **census**, which it has never had" — and today it still has no way

## Open items / tar babies

Named, not chased. Each says why it matters.

1. **TAR BABY — the `jitData`-per-GroupItem model may not survive Phase 2.** Seeding attaches one
   SSA value to a *node*, and emitters write results back onto operand nodes. That is coherent only
   for a single straight-line expression. Loops and multi-statement bodies both fail today. This is
   an architecture question, not a bug — flagged, not investigated.
2. **TAR BABY — `gJitResult` as the return cap is a dominance hazard.** `jitRunAction` rets whatever
   value was emitted last, regardless of which basic block defined it. With a constant it yields
   garbage; with a non-constant it is straightforwardly invalid IR. Coupled to `open-ir-verifier`.
3. **STALE COMMENT, load-bearing.** `ruleActions.rtn:286-291` (and its `.mm` twin at
   `GroupRules.mm:397-401`) states *"jitRunAction still raises generating alongside jitting, so
   generating is checked first."* **`jitRunAction` sets `ruler->generating = 0`**
   (`jitEmitters.rtn:432`). The comment describes the pre-pivot world and will mislead the next
   reader of the dispatcher about which XP handler the JIT uses. (It is `interpretXP`.)
4. **`jitEmitters.rtn:227-229` contradicts `jit.md`'s Phase-1 table and is the correct one.** The
   source comment says unary is not wired; the doc table says DONE with results. The source wins.
   The doc table needs an asterisk — **Tony's or Clay's call, not mine.**
5. **`jitRunIfTest` and `jitRunAddTwo` are hand-built scaffolds, not emit-path code.** They are the
   two green things in `jitIfScratch`. Anyone reading "JIT smoke tests pass" should know these two
   bypass the emitters entirely.
6. **`jit-coverage-recon.md`'s `jitBail` recommendation predates §0.** Its finding 1 proposes
   whole-action fallback for `aCTionFOR` as the design answer. Under §0 that is the divergence §0
   names. Not wrong as engineering; wrong as a *default*. Worth re-reading against §0 before it is
   acted on.
7. **`aCTionFOR` is a tree-walk, not a counting loop** — `jit-coverage-recon.md` finding 1. Under
   "JIT replaces interpreter" this stops being "defer it" and becomes "the JIT must be able to walk
   a GroupItem list," which is a much larger claim. Unresolved, and not this recon's to resolve.

### KANT-8 and the frames end-date, as asked

`CLAIM KANT-8` — `runAction` empties a returned local when `recursive` is set, because
`restoreLocalFields` runs after `processAction` and the returned pointer points into the frame being
restored. **KANT-8 dies in the JIT**: locals become allocas, recursion gets real frames, and
save/restore stops existing (`jit.md` §0 Consequence 1 — `saveLocalFields` is DELETED, not repaired).

Currently-live workarounds that share that same end date, found while in here:

- **"Return the argument, not a local"** — the standing idiom for KANT-8 (`wakeup.md:83-94`). Dies
  with KANT-8.
- **The 2026-07-29 per-frame `saveLocalFields` fix.** §0 already names this a deliberate **bridge**.
  Its fixtures (`iterT1`, `iterT3`, and the pinned-wrong-answer `iterT1m`) are language-level POPs
  and **outlive** the code they were written against — worth keeping straight, because deleting the
  function must not delete the fixtures.
- **Direct-only recursion coverage** (`field.recursive` inferred by identity against
  `currentMETHOD`, `ruleActions.rtn`), which loses locals under mutual recursion `A→B→A`
  (`incant/iterT1m`). Dies with the frame model — real frames do not care who calls whom.
- **The iterator's heap handle and the `isIterator` flag**, including `runOP`'s isIterator exemption
  (`GroupActions.rtn:607-621`) and the two `cerr "not JIT-supported yet"` arms. §0's corollary says
  the iterator becomes **two stack slots** under frames, with no heap node to unwrap — so the
  exemption, the flag, and both refusal arms all go. *Note the irony worth recording: those two
  refusal arms are also the only LOUD-degrade precedent in the tree (`loud-refusal-precedent`). If
  they are deleted, the pattern should be lifted out first.*

## What I could not determine, and what it would cost

Stated plainly, per the loud-refusal-over-quiet-skip rule.

1. **Whether the unary fix is *sufficient* to get `jitscratch` to exit 0.** I could not test it —
   this recon does not edit or build. `jitInc`/`jitDec`/`jitNeg` are the last three fixtures in
   `jitscratch`, so if seeding is the only defect the file goes green; if `jitEmitUnary`'s
   store-back has its own problem it will not. **Cost:** the one-condition edit plus a `tok
   GroupRules.twk` and a rebuild — call it an hour including the retok, and the answer is the run.
2. **The actual IR for any of this.** Every J3 conclusion is outcome-level. No `.ll` was produced,
   because **the tree has no way to produce one** (`no-ir-verifier-no-ir-dump`). This is the single
   biggest limit on this recon's confidence, and it is precisely the trap that produced the
   `jit-gif-branches` disaster on 2026-06-27 — an outcome that looked right. **In particular:
   `jitGifScratch`'s taken→99 / not-taken→11 is suggestive that the gIF branch is now genuinely
   gated post-pivot, and I decline to call it proven.** **Cost:** roughly three lines
   (`mod->print(llvm::errs(), nullptr)` before `addIRModule`, plus a `verifyFunction`), a retok and
   a rebuild. **This is the highest value-per-hour item in the whole recon** and I would do it
   before anything else on the list.
3. **The exact mechanism of the ICmp abort.** `jitdata-single-value-clobber` is `inferred` and
   reads convincingly — which, per bear-trap #19's corollary, is exactly when to distrust it. *A
   hypothesis that survives narrowing is not thereby confirmed; narrowing is only valid inside the
   space you are searching.* I did not search outside `jitEmitters.rtn` and `Instruct.rtn`. **Cost:**
   the IR dump above answers it immediately — the invalid `icmp` would be visible in the text.
4. **Whether the 24 ungated ops and 29 ungated handlers are *individually* reachable inside a
   realistic jitted body.** I proved the mechanism (`testPrint`) and enumerated the population; I did
   not exercise 53 constructs one at a time. **Cost:** one probe fixture per construct, mechanical
   but slow; better spent after a refusal mechanism exists, since the refusal itself would then
   report the population for free.
5. **Whether `jitEmitGIF` nests.** `gIfEndBlocks` is a stack so it is *provided for*; `testGXLeaf`
   (two sequential ifs) segfaults before nesting can be reached. **Cost:** blocked behind items 1-3.
6. **Nothing about performance.** No jitted-vs-interpreted timing was taken, and under §0 it is not
   the point — but if anyone is carrying an "is the JIT faster yet" question, this recon does not
   touch it.
